What each step contains changes with the purpose of the task (deliver, learn, restore, decide), but the frame does not. The 4 gates decide where to stop (2.4). The size of a request decides only one thing: whether to split it into several slices (2.5). Each slice goes through all 8 steps.

Part 2

Layer 1 · Global: how we work, for every task

Applies to writing code, writing documents, research, making video, data analysis. Nothing in this layer assumes the task is software, except the Stop hook (see 2.8). The workflow is only a guide: it names no path, file or skill. Paths live in places.md, and a skill is called by what it does.

2.3 Frame: four questions decide how to work

1. Purpose?deliver a change · learn something · restore · reach a decision
2. What is "correct"?known (examples) · findable (a reference) · judged by the viewer · none
3. What if it is wrong?reversible or not · wide or narrow impact
4. Who approves?you are present · you are absent
▼ leads to
Delivergated by the cost of a mistake, not by the amount of code: 4 gates decide where to stop (2.4) · a large request is split into slices (2.5)
Learntime-boxed · output is an answer + evidence · throwaway code needs no tests
Restorereduce damage with a reversible action → hypothesis, experiment, elimination → the root fix goes through Deliver
Decidebrief the options (Asking for a decision shape) → decision record
Judged by the viewershow a draft early, fix from feedback
Irreversibledry run on a copy · backup · rollback plan → ◀ ask before that step
No one to approvedo only what is reversible, stop before the rest, leave a report

2.4 Four gates: where to stop

They replace the Small/Medium/Large table. Each gate is a yes/no question, asked at the right step. Each "yes" adds one stop or one file. If every answer is "no", do the work and report.

G1 · at ③ AgreeWrite the acceptance examples first. Is any value the user would see (label, format, message, default) set by Claude, not coming from the request, the code or you? → show the examples, mark them assumed ◀ wait · a value you set that the user does not see: decide it yourself, write [decided]
G2 · at ④ PlanDoes it need more than one logical change, so more than one commit? → plan, one change per step ◀ approve · several deliverables, more than 3 steps, or several requests in one message? → a map of slices ◀ approve the map once (2.5)
G3 · before every stepIs the next step hard to undo: API, data model, stored data, security, migration, anything published? → say what it breaks, ask how to roll it out, even when the request was explicit ◀ ask
G4 · at ③ AgreeWill the work outlive this session, or run while no one is watching? → the spec becomes a file

Why it changed (1 Nov).You still had to approve every step. Three rules caused most of the stops: stop after each step, G1 waits on any assumed value, and one question per message. Now G1 stops only for values the user would see, each step reports one line and moves on, questions are batched at one approval point, and every question comes with a recommendation. The 25 Oct lesson keeps G1 at this level: the temporary-password format sat among 22 examples and was rejected only after the code was written. Not yet measured on real tasks.
Why the table was dropped, and what was measured (11 Oct).A task has several independent properties; the table forces one label and does not say which row wins when several match. Claude was asked to classify 8 tasks, 5 times each: the old table gave the same label on 5/8 tasks, the 4 gates gave the same combination on 6/8 tasks and the same gate answers on 30/32 answers. Real behaviour, asking before changing a public API field: old table 5/6, first version of the gates 7/12, strict G3 11/12. Renaming an internal variable across 4 files: both versions just did it, 3/3.

2.5 Large requests: map and slice

Before, one large request became one large spec, which led to a large plan and a large diff, so it was very hard to review. Now a large request is split into several slices. Each slice has one behaviour the user can see, at most 3 steps, and goes through its own 8 steps. The map keeps each slice's place in the whole system.

The product never refers back to the work.Reading docs/product/ shows the current truth, without wading through history. To learn why, go to .work/.

.work/ is a hidden folder

Ripgrep, the search tool under Claude Code, skips hidden folders by default. CLAUDE.md gives the explicit path (.work/lessons.md) so Claude reads it directly, without depending on search.

status.json is not committed

It is machine-generated and changes on every test run, so committing it would add noise to diffs. CI regenerates it when needed. Only the final snapshot is kept when the task is archived.

ADRs sit on the product side

They come out of work, but they explain why the system is built the way it is and live with the system, so with the layer-2 kit they go in docs/product/decisions/. A repo without the kit uses its existing ADR folder; if there is none, Claude proposes docs/decisions/ and waits. Append only, never edit an old ADR: when a new decision replaces one, write a new ADR that points back to the old one.

Paths are defaults

The tree above is the default of places.md and of the layer-2 kit. A project can change it in CLAUDE.md. A repo with the layer-2 kit must keep .work/, because the CI trace.yml reads .work/tasks/*/spec.md, only one level deep. That is why a slice sits beside the map's folder rather than nested inside it, and the map's folder has no spec.md, so CI skips it.
