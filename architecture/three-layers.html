Three-layer architecture applied to SDLC and STLC

Layer 1 is the shared frame used for every task. Layer 2 is the part specific to each project. Layer 3 is the artifacts that live in the repo and are passed from one stage to the next. The requirement id (REQ-…) is the thread that ties the artifacts together. This is the view as SDLC and STLC matrices, updated 1 Nov 2026. Everything on this page has been built. A fuller overview is overview.html.

Shared node: requirement analysis

SDLC and STLC read the same input, so the analysis is done once with two lenses, not split into two activities. The shared output is the acceptance examples: they are both the target for dev to build and the test cases for QA to check. This is the Three Amigos practice from BDD: PO, dev and QA analyse together, once.

The REQ thread links SDLC and STLC

The requirement id runs through every artifact, so the question "does this requirement have a test yet, and which release shipped it" becomes a question a script can answer.

requirement
REQ-CHECKOUT-012→ task spec
Changes: REQ-012 (new)→ test plan / design
boundaries, decision table→ test
test_REQ_CHECKOUT_012_…→ commit / PR
"REQ-012: …"→ trace-check
REQ-012 ✓→ release
CHANGELOG→ incident
BUG-88 → REQ-012
A task is done only when the requirement is updated.The task spec records which REQs are added or changed. The "Done when" step includes editing the requirement file, so the docs do not drift away from the code.
The strongest mechanism in layer 2 is CI.CI runs independently of Claude, on every PR, including code written by people. The Stop hook is only an early stop while working.
All 7 layer 2 skills are built.They live in the package's project-kit/ and are installed into a repo with project-init. No real task has used them yet. The next step is one PR that must be blocked and one PR that must pass, in a TypeScript project.
