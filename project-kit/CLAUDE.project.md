## How this project works

Test command: `npm test`

### Where things live

- **Product** (what the system is; changes only when the product changes):
  - `docs/product/requirements/<area>.md`: requirements and their examples
  - `docs/product/test-cases/<area>.md`: test design per requirement
  - `docs/product/architecture/`: how the system is built
  - `docs/product/decisions/NNNN-<name>.md`: decision records, only added, never edited
- **Work** (how it got that way; one folder per piece of work):
  - `.work/tasks/<yyyy-mm-dd>-<name>/`: `spec.md`, `status.json` (generated);
    a split request keeps `map.md` there instead, its slices in `<yyyy-mm-dd>-<name>-s1/`, `-s2/`…
  - `.work/test-plans/`, `.work/test-runs/`, `.work/releases/`, `.work/incidents/`
  - `.work/lessons.md`: this project's lessons
- `.work/` is hidden: read and write it by path, never rely on search to find it.
- Work changes the product docs; product docs never point into `.work/`.

### When the project's tools apply

- **The project skills, at any tier.** Load the one whose description matches
  the task: writing tests → `test-design` then `test-authoring`; fixing a bug
  or a failing test → `bug-report`; adding or changing an interface →
  `api-contract`; an unclear request → `requirement-review`. They work from the
  request and the code when no requirement file exists.
- **The requirement files, named examples and trace-check, at T3 only:** a
  product rule that outlives the task is added, changed or dropped. A bug fix,
  a refactor, or a feature that changes no lasting rule needs no requirement
  file and no trace-check.

### Requirements

- Id: `REQ-<AREA>-NNN`, e.g. `REQ-CHECKOUT-012`. AREA is the file name in
  capitals. Numbers are never reused; a dropped requirement gets
  `Status: deprecated` and stays in the file.
- Every requirement has examples `ex1`, `ex2`…, each with real values. An
  example not yet confirmed by its owner is marked `` `assumed` ``.
- Every test that proves an example names it in its title:
  `it("REQ-CHECKOUT-012 ex1: 10% + 5% on 100,000 → 85,500", …)`, or in
  Python, where a name cannot hold `-`, `def test_REQ_CHECKOUT_012_ex1_stacked_coupons():`.
  A test for a behaviour with no example means a missing example: add it to
  the requirement first (`requirements` skill).
- A task spec lists the requirements it changes under `## Changes`, one per
  line: `- REQ-CHECKOUT-012 (new)` · `(changed: ex2)` · `(deprecated)`.

### Proving a task (T3)

```
npm run test:ci          # writes reports/*.xml (JUnit)
node scripts/trace-check.mjs --results unit=reports/unit.xml \
  --results e2e=reports/e2e.xml \
  --task .work/tasks/<task>
```

Python: the first line is `python3 -m pytest --junitxml=reports/unit.xml`
(pytest also runs `unittest` tests), and trace-check still needs Node 18+.

`status.json` is generated by this command; never write it by hand. A task
is done when trace-check exits 0 for its task folder. Before a release run it
with `--strict` over all requirements.

TypeScript/JavaScript only: `npm run coverage:map` writes `docs/coverage/COVERAGE-MAP.html` (generated,
never edited): which examples have a test and which differ from the code. It
reads test files without running them, so it shows what is linked, not what
is proven.

### Skills for this project

The skills in `.claude/skills/`, loaded when a task matches their
description. The global workflow frames the task and sets its tier first.
